# Tech debt

Known shortcuts, deferred work, and things left deliberately unfinished — logged so they're a choice, not a surprise. Format: what/why/impact/where. Remove an entry once it's actually fixed rather than leaving it marked done.

---

**What still scans whole tables at 79k-contact scale.**
What: two leftovers after the referenced-ids sweep, plus the migration fallbacks. (1) Calendar still ships **all events and jobs** ever created; bounded today, but the archive only grows — a date-window fetch is the eventual cure. (2) The estimates list is **unwindowed** — every document `select("*")` into an unvirtualized table; fine at 78 documents, the next 79k-shaped problem as document history grows. Marketing Analytics is served aggregates for every range now (0164); until that migration is run in Supabase its fallback reduces the window's leads server-side, and All Time's fallback is a full scan. Also: Salespeople falls back to a full server-side scan until migration 0156 is run — slower, same numbers, browser unaffected — and the dashboard's fallback (until 0162 runs) scans the open-stage book server-side for its stage panel, exactly the cost the old dashboard paid on every load. Why: each is behind an explicit user choice or growth that hasn't happened yet. Impact: none day-to-day. Where: `src/app/(app)/calendar/page.tsx`, `src/app/(app)/estimates/page.tsx`, `src/lib/actions/marketing-analytics.ts`, `src/app/(app)/salespeople/page.tsx`, `src/lib/actions/dashboard.ts`.

**Dashboard box drag is mouse-only, and two KPI cards have no sparkline.**
What: rearranging the dashboard's boxes uses HTML5 drag on the panel headers — desktop pointer only, no keyboard or touch reorder (the phone dashboard keeps its own fixed layout, so nothing is lost there today). Separately, the KPI row's leads/appointments cards carry no sparkline because the 12-month series only holds money (adding monthly lead/appointment counts to the rollup is the cure). Why: the funnel cards set the drag idiom and it shipped proven. Impact: cosmetic; a keyboard user still sees every panel in the saved order. Where: `src/app/(app)/dashboard-view.tsx`, `src/lib/data/dashboard-rollup.ts` (`months`).

**The sales-team audit trail only sees `saveSalesTeam`.**
What: `sales_team_changes` (0154) is written by the server action, so an edit to the seat columns that bypasses it — a direct SQL update in the Supabase console, or a future code path that writes `estimates.sales_rep_1` etc. itself — leaves no trail; the signature-time seeding trigger (0135/0153) also stamps seats without a row, so the trail starts at the first post-signature save. Why: the action is the only in-app path that edits these columns after signature, and a trigger-based capture runs on service-role paths where `auth.uid()` is null (024's constraint) — chosen simple and testable over airtight. Impact: none in normal use; an admin editing the database by hand is already outside every guard. A `before update` trigger on the eight columns would close it. Where: `src/lib/actions/rep-commission.ts` (`saveSalesTeam`), `supabase/migrations/0154_sales_team_changes.sql`.

**Cobrowse batches ship as uncompressed JSON.**
What: rrweb event batches cross Supabase Realtime as plain JSON chunks (`src/lib/cobrowse/wire.ts`); a full snapshot of a heavy page can be a couple dozen 50KB parts. Why: `CompressionStream` would cut that ~5-8x but adds async plumbing and a base64 step, and the first version favored a wire simple enough to unit-test exactly. Impact: none on wifi/LTE; on very weak site cellular the first snapshot may take a few seconds to land. Where: `src/lib/cobrowse/wire.ts`, `src/lib/cobrowse/recorder.ts`.

**A hard page reload ends a cobrowse share.**
What: the rrweb recorder lives in the (app) layout's React tree, so client-side navigation survives a share, but a full reload (or the browser killing the tab) drops the session without a goodbye; the stale row ages out via the existing 4-hour abandoned-share cutoff and the viewer sees a frozen mirror until they leave. Why: same lifetime the WebRTC share already has (`beforeunload` teardown is best-effort); persisting a session across reloads means rejoin tokens in storage for a rare case. Impact: rare, self-healing, viewer inconvenience only. Where: `src/app/(app)/screen-share.tsx`.

**During a deploy, an old client can join a cobrowse session it can't render.**
What: clients built before `kind` existed treat every share row as WebRTC and send a `viewer-hello` expecting an SDP offer; against a cobrowse sharer they wait on a picture that never comes (and occupy the one viewer slot until they leave). Why: transient deployment skew only — the update popup already nudges stale tabs onto the new build. Impact: minutes-long window per deploy, worst case one confused viewer. Where: resolves itself; remove this entry once the cobrowse release is deployed.

**A CSV import chunk whose response is lost may be re-sent on Resume.**
What: the import uploads 2,000-row chunks and advances its resume cursor only after a chunk's response arrives; if the connection drops after the server inserted a chunk but before the browser heard back, Resume sends that chunk again and duplicates up to 2,000 rows. Why: true exactly-once would need an idempotency key per chunk and a server-side ledger — real plumbing for a narrow window that only opens on a mid-request connection loss. Impact: rare; visible immediately (contact count runs ~2,000 high) and recoverable by deleting the doubled rows or re-running the duplicate check on a fresh import. Where: `src/app/(app)/pipeline/csv-import-panel.tsx` (`runImport`), `src/lib/actions/leads.ts` (`bulkImportLeads`).

**Observability now skips server actions, uploads, AI calls, and self-caught route errors.**
What: the external-facing routes (Stripe webhooks, SMS/email/leads/Meta webhooks, all cron jobs) run under `withRouteObservability` and `sendEmail` failures reach Sentry (#031) — but server actions other than `logCall` still have no wrapper, uploads and AI requests log ad hoc, and a webhook that catches its own failure to answer 200 reports "completed" with only a bare `console.error` inside. The high-frequency poll routes are excluded deliberately. Why: the rollout took the highest-value, lowest-noise slice first. Impact: an action-level failure (a save that errors server-side) still has no correlation id or capture. Where: `src/lib/observability/observe.ts` callers; "Known gaps" in `docs/features/observability.md` (which also still lists the Turbopack source-map and `src/proxy.ts` gaps).

**Whole-book lead fetches are gone from pages; watch new code for the pattern.**
What: every page that shipped the whole contact book to the browser has been cured — dial queue (DECISIONS #019), pipeline board (#020), contacts, and the report/analytics pages plus the duplicate-merge tool (#021). `grep -rn 'selectAll<Lead>' src/` should stay empty of `select("*")` page fetches; the remaining full-row `selectAll` callers are server-side jobs (backup, Drive sync) whose output genuinely needs every row. Why kept as a note: the pattern is easy to reintroduce — a new page that "just needs the leads" one prop away from a 79k-row payload. Where: patterns to copy are `src/lib/actions/dial-contacts.ts`, `pipeline-board.ts`, `contact-list.ts`, and `src/lib/data/lead-lite.ts`.

**Every To/Cc/Bcc recipient on a sent estimate shares one single-use portal link.**
What: `sendEstimateToCustomer` mints exactly one login token/link per send and puts the identical link in the one email that goes to every To/Cc/Bcc address (primary customer, second-contact co-owner, any free-typed extras) — because portal access is per-lead, not per-person (decision #005). Why: minting a distinct token per recipient would fix it but wasn't done as part of moving to real To/Cc/Bcc (decision #022), to keep that change to "one real email instead of a loop," not also change the token's per-lead semantics. Impact: softened to an extra step rather than a dead end — the second opener now lands on the portal login page with the failure explained and the email form right there, and that form matches the second contact's email too, so a co-owner self-serves a fresh link (DECISIONS #030). Residual: a free-typed extra recipient (a Cc'd project manager, say) isn't on the lead and still isn't matched — they go through the rep (Copy link / Send again). Where: `src/lib/actions/estimates.ts` (`sendEstimateToCustomer`, the `link` built once and passed to a single `sendEmail` call covering every recipient); the fix, if ever warranted, is a `createLoginToken` call per recipient, same as `sendPortalLink` already does per channel.

**Commission payout removals leave no trail, and the dispatcher scheme has no payment tracking.**
What: `rep_commission_payouts` rows (0158) are insert-and-delete only — Remove (Office/Admin, confirmed in plain words) deletes the row outright, so a removed payment or advance leaves no record it was ever there, unlike seat edits, which log to `sales_team_changes`. Separately, the dispatcher commission page still has no payout ledger at all — the same "payable forever" behavior the rep page just cured. Why: matched to the manual-customer-payments discipline (remove and re-record) so 0158 stays one paste; a `_changes` mirror of 0154 is the known cure if a payroll dispute ever needs one. Impact: an admin can erase a recorded advance without trace; `recorded_by`/`created_at` survive only as long as the row does. Where: `supabase/migrations/0158_rep_commission_payouts.sql`, `src/lib/actions/rep-commission.ts` (`removeCommissionPayout`); dispatcher side untouched at `src/app/(app)/commissions/`.

**The portal can't collect the remainder of a partially paid phase online.**
What: once any settled payment is filed to a phase, the customer portal shows "Partially paid — $X still due" with no Pay button: `startPhaseCheckout` charges the full face amount and refuses a phase with any settled payment, so a button there would either overcharge or error. The remainder is collected offline and recorded by hand (manual payments). Why: partial payments got honest display first (DECISIONS #033); a remainder checkout means the Stripe session amount, the pending row and the webhook all learning owed-not-face-value, changed together and tested against a real account. Impact: small — a customer who part-paid finishes the invoice offline, which is what already happens today; the office just now sees the remainder everywhere. Where: `src/lib/actions/portal-payments.ts` (`startPhaseCheckout`), `src/app/portal/estimates/[id]/phase-payments.tsx`.

**The single-project report's net cash ignores commission paid.**
What: `/projects/[id]/report` computes its rollup without `commissionCents`, so its "Net cash (collected − spent)" reads higher than the Projects list shows for the same job once a commission payment is recorded against it (#035). Why: that report has a client view and pay must never print for a customer; splitting its figures by audience was more surface than the ask needed. Impact: an owner comparing the two sees different net cash with the arithmetic named in each label; the list and the projects report are the internal truth. The cure, if wanted: pass commission only when `!clientView` and label both variants. Where: `src/app/(app)/projects/[id]/report/page.tsx`. Also: Profit & Loss (`/profit-loss`) still excludes commission entirely.

**The AI assistant refetches its whole context on every question.**
What: each POST to `/api/ai-assistant` re-runs the full gather — lead roster + whole-book totals, events, tasks, every estimate, `buildProjectCards` (eight `selectAll` fans over payments/expenses/bills), a 30-day call window — even when the follow-up arrived ten seconds after the last answer. Prompt caching makes the model side cheap; the database side still pays a Projects-page-sized query set per turn. Why: a per-conversation server cache needs a store and an invalidation story, and the first streaming version kept the same "fetch fresh under the caller's RLS" shape every page uses. Impact: fine at today's volume; a chatty session is a handful of page-loads' worth of queries. The cure if it grows: cache the built context per user for a few minutes, or move the heavy sections to fetch-on-demand tools. Where: `src/app/api/ai-assistant/route.ts` (`gatherContext`).

**Assistant voice input is only as good as the browser's speech engine.**
What: the mic on the AI assistant uses the Web Speech API, so recognition quality, language handling and availability are whatever the person's browser ships — Chrome/Edge/Safari carry it, Firefox doesn't (the mic simply doesn't render there), and a loud job site may transcribe poorly with no knob for us to turn. Why: zero cost, zero vendor setup, and the typed input stays the always-works path, which is the right first version to learn whether reps actually talk to it. Impact: a misheard question costs one correction; unsupported browsers lose nothing they had. The cure if usage proves out: a server-side transcription service (per-company key, same encrypted-secrets pattern as Twilio) feeding the same `mergeTranscript` seam so the UI doesn't change. Where: `src/lib/voice-input.ts`, `src/app/(app)/ai-assistant-button.tsx`.

**`events_update_dispatch` still reads `leads` inline — the dormant half of the 0152 recursion.**
What: the dispatch update policy on `events` carries a raw `EXISTS (select … from leads …)` in its expression (0090/0094, restated by 0117). That was one of the two edges of the cycle that broke every appointment save when 0152 added the reverse edge to `leads_select`; 0159 broke the leads side, so this one is inert — but any future migration that names `events` inline in any leads policy re-detonates the same error. Why left: the events policies carry hand edits made in the live database (0148's lesson), the function it would swap to (`dispatcher_may_touch_lead`) exists only in the live DB with no definition in this repo to verify against, and one broken edge is all a cycle needs. Impact: none today; the trap only springs if DECISIONS #039's rule is ignored. The cure: restate the policy against a repo-defined `security definer` helper next time dispatch scoping is touched on purpose. Where: `supabase/migrations/0117_rls_evaluate_once_everywhere.sql` (`events_update_dispatch`), DECISIONS #039, `src/lib/data/lead-visibility-rules.test.ts` (pins the leads side).

**The AI receptionist pauses between turns and can't be interrupted.**
What: each exchange is a Twilio `<Gather>` round-trip — ASR finalizes, one Claude turn, TTS — so the caller hears a two-to-three-second beat before each reply and can't talk over the AI the way they could a person; a mid-call hangup also leaves the lead to the sweep (instant on the next inbound call, 2-hourly cron floor otherwise), and the voice is one fixed English Polly voice. Why: this ships on the existing Vercel + per-company-Twilio stack with zero new vendors; the full-duplex build (Twilio ConversationRelay + Claude) needs an always-on WebSocket server Vercel can't host, which is real infrastructure the pilot doesn't justify yet. Impact: it reads as a very good answering service, not a human — acceptable for missed/after-hours calls, and honest since it announces itself as an AI. The cure when the pilot proves out: a small WS service (Fly/Railway) speaking ConversationRelay, reusing the same tested conversation-policy module; per-company voice/language settings ride along. Where: `src/lib/ai-receptionist-engine.ts`, `src/app/api/voice/ai/turn/route.ts`, DECISIONS #040.

**A penciled AI appointment is silent until a rep is assigned, and knows no business hours.**
What: events the AI receptionist pencils in carry `assigned_to` null, and the appointment-reminder cron only texts events with an assigned rep — so the night-before/hour-before reminders start only after the dispatcher assigns someone; and the AI will happily pencil a Sunday or a holiday, because it has no notion of the company's working days. Why: unassigned-by-design keeps the dispatcher's morning routine as the control point (decision #043), and business-hours rules don't exist as data anywhere in the schema yet. Impact: small — the immediate "reply YES to confirm" text goes out at once, and a bad day costs one correction call. The cure when it matters: a per-company working-days/hours setting the prompt and `appointmentFromExtraction` both respect, and either assigning a default dispatcher or letting the reminder cron accept unassigned events. Where: `src/lib/ai-receptionist-engine.ts` (finalize), `src/app/api/cron/appointment-reminders/route.ts` (the `assigned_to` filter).

**The rep-report funnel doesn't know about partnerships.**
What: the Salespeople grid splits a partnership sale between both reps (0163), but the marketing-analytics rep-report funnel still attributes every lead to `assigned_to` alone — a partner sees the shared job in their portal and their tallies on the grid, yet that same sale is missing from their printable funnel (it appears only in the owner's). Why: the funnel is a per-rep pipeline story (leads in → appointments → signed) built lead-by-lead in `funnelFor`, and folding half-credit into every stage of it is a bigger judgment call than the grid's four tallies — half an appointment makes no sense even where half a sale does. Impact: low today — partnerships are new and the grid is the leaderboard people quote. The cure: decide per stage what a partner half-owns (probably: leads and signed value split, appointments counted where they sat either chair — which the funnel already does), then apply it in `funnelFor`. Where: `src/app/(app)/marketing-analytics/rep-report/page.tsx`, DECISIONS #050.
