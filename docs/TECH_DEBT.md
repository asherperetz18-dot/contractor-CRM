# Tech debt

Known shortcuts, deferred work, and things left deliberately unfinished — logged so they're a choice, not a surprise. Format: what/why/impact/where. Remove an entry once it's actually fixed rather than leaving it marked done.

---

**What still scans whole tables at 79k-contact scale.**
What: two leftovers after the referenced-ids sweep, plus the migration fallbacks. (1) Calendar still ships **all events and jobs** ever created; bounded today, but the archive only grows — a date-window fetch is the eventual cure. (2) The estimates list is **unwindowed** — every document `select("*")` into an unvirtualized table; fine at 78 documents, the next 79k-shaped problem as document history grows. A very wide **custom** date range on Marketing Analytics still fetches its whole slice (All Time itself is served aggregates now, 0157). Also: Salespeople and analytics All Time fall back to full server-side scans until migrations 0156/0157 are run in Supabase — slower, same numbers, browser unaffected. Why: each is behind an explicit user choice or growth that hasn't happened yet. Impact: none day-to-day. Where: `src/app/(app)/calendar/page.tsx`, `src/app/(app)/estimates/page.tsx`, `src/lib/actions/marketing-analytics.ts`, `src/app/(app)/salespeople/page.tsx`.

**The sales-team audit trail only sees `saveSalesTeam`.**
What: `sales_team_changes` (0154) is written by the server action, so an edit to the seat columns that bypasses it — a direct SQL update in the Supabase console, or a future code path that writes `estimates.sales_rep_1` etc. itself — leaves no trail; the signature-time seeding trigger (0135/0153) also stamps seats without a row, so the trail starts at the first post-signature save. Why: the action is the only in-app path that edits these columns after signature, and a trigger-based capture runs on service-role paths where `auth.uid()` is null (024's constraint) — chosen simple and testable over airtight. Impact: none in normal use; an admin editing the database by hand is already outside every guard. A `before update` trigger on the eight columns would close it. Where: `src/lib/actions/rep-commission.ts` (`saveSalesTeam`), `supabase/migrations/0154_sales_team_changes.sql`.

**Cobrowse batches ship as uncompressed JSON.**
What: rrweb event batches cross Supabase Realtime as plain JSON chunks (`src/lib/cobrowse/wire.ts`); a full snapshot of a heavy page can be a couple dozen 50KB parts. Why: `CompressionStream` would cut that ~5-8x but adds async plumbing and a base64 step, and the first version favored a wire simple enough to unit-test exactly. Impact: none on wifi/LTE; on very weak site cellular the first snapshot may take a few seconds to land. Where: `src/lib/cobrowse/wire.ts`, `src/lib/cobrowse/recorder.ts`.

**A hard page reload ends a cobrowse share.**
What: the rrweb recorder lives in the (app) layout's React tree, so client-side navigation survives a share, but a full reload (or the browser killing the tab) drops the session without a goodbye; the stale row ages out via the existing 4-hour abandoned-share cutoff and the viewer sees a frozen mirror until they leave. Why: same lifetime the WebRTC share already has (`beforeunload` teardown is best-effort); persisting a session across reloads means rejoin tokens in storage for a rare case. Impact: rare, self-healing, viewer inconvenience only. Where: `src/app/(app)/screen-share.tsx`.

**During a deploy, an old client can join a cobrowse session it can't render.**
What: clients built before `kind` existed treat every share row as WebRTC and send a `viewer-hello` expecting an SDP offer; against a cobrowse sharer they wait on a picture that never comes (and occupy the one viewer slot until they leave). Why: transient deployment skew only — the update popup already nudges stale tabs onto the new build. Impact: minutes-long window per deploy, worst case one confused viewer. Where: resolves itself; remove this entry once the cobrowse release is deployed.

**A CSV import chunk whose response is lost may be re-sent on Resume.**
What: the import uploads 2,000-row chunks and advances its resume cursor only after a chunk's response arrives; if the connection drops after the server inserted a chunk but before the browser heard back, Resume sends that chunk again and duplicates up to 2,000 rows. Why: true exactly-once would need an idempotency key per chunk and a server-side ledger — real plumbing for a narrow window that only opens on a mid-request connection loss. Impact: rare; visible immediately (contact count runs ~2,000 high) and recoverable by deleting the doubled rows or re-running the duplicate check on a fresh import. Where: `src/app/(app)/pipeline/csv-import-panel.tsx` (`runImport`), `src/lib/actions/leads.ts` (`bulkImportLeads`).

**Observability now skips server actions, uploads, AI calls, and self-caught route errors.**
What: the external-facing routes (Stripe webhooks, SMS/email/leads/Meta webhooks, all cron jobs) run under `withRouteObservability` and `sendEmail` failures reach Sentry (#031) — but server actions other than `logCall` still have no wrapper, uploads and AI requests log ad hoc, and a webhook that catches its own failure to answer 200 reports "completed" with only a bare `console.error` inside. The high-frequency poll routes are excluded deliberately. Why: the rollout took the highest-value, lowest-noise slice first. Impact: an action-level failure (a save that errors server-side) still has no correlation id or capture. Where: `src/lib/observability/observe.ts` callers; "Known gaps" in `docs/features/observability.md` (which also still lists the Turbopack source-map and `src/proxy.ts` gaps).

**Whole-book lead fetches are gone from pages; watch new code for the pattern.**
What: every page that shipped the whole contact book to the browser has been cured — dial queue (DECISIONS #019), pipeline board (#020), contacts, and the report/analytics pages plus the duplicate-merge tool (#021). `grep -rn 'selectAll<Lead>' src/` should stay empty of `select("*")` page fetches; the remaining full-row `selectAll` callers are server-side jobs (backup, Drive sync) whose output genuinely needs every row. Why kept as a note: the pattern is easy to reintroduce — a new page that "just needs the leads" one prop away from a 79k-row payload. Where: patterns to copy are `src/lib/actions/dial-contacts.ts`, `pipeline-board.ts`, `contact-list.ts`, and `src/lib/data/lead-lite.ts`.

**Every To/Cc/Bcc recipient on a sent estimate shares one single-use portal link.**
What: `sendEstimateToCustomer` mints exactly one login token/link per send and puts the identical link in the one email that goes to every To/Cc/Bcc address (primary customer, second-contact co-owner, any free-typed extras) — because portal access is per-lead, not per-person (decision #005). Why: minting a distinct token per recipient would fix it but wasn't done as part of moving to real To/Cc/Bcc (decision #022), to keep that change to "one real email instead of a loop," not also change the token's per-lead semantics. Impact: softened to an extra step rather than a dead end — the second opener now lands on the portal login page with the failure explained and the email form right there, and that form matches the second contact's email too, so a co-owner self-serves a fresh link (DECISIONS #030). Residual: a free-typed extra recipient (a Cc'd project manager, say) isn't on the lead and still isn't matched — they go through the rep (Copy link / Send again). Where: `src/lib/actions/estimates.ts` (`sendEstimateToCustomer`, the `link` built once and passed to a single `sendEmail` call covering every recipient); the fix, if ever warranted, is a `createLoginToken` call per recipient, same as `sendPortalLink` already does per channel.
