# Sales Pipeline & Leads

Everything about a lead as a sales record: the pipeline board, dialing, CSV import, refunds, and the contact list.

| Feature | Status | Description | Code |
|---|---|---|---|
| Pipeline board | shipped | Kanban-style board of leads by stage, with per-lead panels for notes, tasks, calls, messages, appointments, files, and view history. Companion tabs render inline rather than as separate pages. Board data is server-windowed (`getPipelineBoardData`: each stage's first 40 cards + exact counts, stat tiles as computed numbers, per-lead panels fetched on card open) — the page once shipped every lead, task, note, and file to the browser, which at 79k contacts took minutes to open. See DECISIONS #020. | `src/app/(app)/pipeline/page.tsx`, `pipeline-board.tsx`, `lead-form.tsx`, `notes-timeline.tsx`, `tasks-panel.tsx`, `calls-panel.tsx`, `messages-panel.tsx`, `lead-appointments-panel.tsx`, `lead-files-panel.tsx`, `lead-view-trail.tsx`, `src/lib/actions/pipeline-board.ts`, `src/lib/pipeline-aggregates.ts` |
| Bulk email selected contacts | shipped | Multi-select checkboxes in both the Contacts table and Pipeline board (a "Select" toggle there, since cards are otherwise draggable) let office/sales staff write one subject/message and send it individually to every selected contact with an email on file, via the same Resend pipeline as the portal-link send. One bad address never blocks the rest of the batch; contacts with no email are reported as skipped. Gated by `canEditDispatch` (Office/Sales/Dispatch/Admin), same as editing a lead. | `src/lib/bulk-email.ts`, `src/lib/actions/bulk-email.ts`, `src/components/bulk-email-modal.tsx`, `contacts-table.tsx`, `pipeline-board.tsx` |
| Attention digest | shipped | Per-lead warning badges surfaced on the pipeline (no appointments, no notes, no tasks, stale notes, overdue task by N days) so a rep can see which leads are being neglected at a glance. | `src/app/(app)/pipeline/attention-digest.tsx` |
| CSV/XLSX lead import | shipped | Column-mapping UI (name, phone, email, address, project type, value) reading `.xlsx`/csv client-side via the `xlsx` package, with duplicate detection before bulk insert. Handles spreadsheet scale (70k+ rows): uploads in 2,000-row chunks with live progress and a Resume that continues a failed run where it stopped; duplicates are matched in the browser against a downloaded key set of every existing contact (see decision #017). | `src/app/(app)/pipeline/csv-import-panel.tsx`, `src/lib/import-batching.ts`, `src/lib/actions/leads.ts` (`bulkImportLeads`, `getExistingContactKeys`) |
| Three phone numbers per contact | shipped | `phone2`/`phone3` on the lead (migration 0150): bought cold-call lists often carry up to three numbers for one person. Editable on the contact card (Phone 2 / Phone 3, with Call buttons), mappable in the CSV importer, counted by both duplicate checks, and matched by the caller matcher (TS `phone-match.ts` and the SQL `create_lead_for_unknown_caller`) so a prospect ringing back on any of their numbers isn't minted as a new contact. Inbound SMS matching and the dial queue still read only `phone`/`second_contact_phone` (see TECH_DEBT). | `supabase/migrations/0150_lead_phone2_phone3.sql`, `src/lib/data/phone-match.ts`, `src/app/(app)/pipeline/lead-form.tsx`, `csv-import-panel.tsx`, `src/lib/actions/leads.ts` |
| AI lead-conversation analysis | shipped | On-demand Claude analysis of a lead's message/call history rendered on the contact card; stays visible once generated even if the feature toggle is later switched off, since it's treated as a record rather than a live indicator. | `src/app/(app)/pipeline/lead-analysis-panel.tsx`, `src/lib/actions/lead-analysis.ts`, `src/lib/data/ai-analysis.ts` |
| Estimate-driven stage auto-advance | shipped | Sending/signing an estimate can move a lead's pipeline stage automatically (e.g. into "Proposal Sent" or "Won"), because the hand-maintained stage field routinely went stale relative to what actually happened on the estimate. Looks up the company's own (editable, per-company) stage names first and no-ops if the target stage was renamed/deleted. Won't drag a lead backwards past stages like Lost/DNC. | `src/lib/pipeline/advance-stage.ts` |
| Dial queue / sales dialer | shipped | Sequential call-through session over a filtered lead list with disposition logging, mid-call quick-edit of lead fields, inline appointment booking, and note-taking, gated to sales-center-enabled roles. List building is server-paged (`listDialContacts`, 50 rows + total per request) — the page once shipped every lead to the browser to filter there, which at 79k contacts took minutes to open; full Lead rows travel only for a session's selected contacts. See DECISIONS #019. Sessions warn "already called N× today" (rep's calendar day) and pause auto-dial on those contacts; a completed session clears its selection and closing one refreshes the list. The By Lead tab's Call Status (Not Called Yet / Called Before) and Disposition (latest-outbound-call outcome) filters — both judged over outbound calls only — combine with the stage filter to build a fresh-dial or redial list for any pipeline stage. | `src/app/(app)/dial-queue/`, `src/lib/actions/dial-contacts.ts`, `src/lib/dial-filters.ts`, `src/lib/actions/call-logs.ts` |
| Lead refunds | shipped | Tracks refund requests against a lead (Requested/Received/Denied) with age-in-days and CSV export. | `src/app/(app)/lead-refunds/`, `src/lib/actions/leads.ts` (`resolveLeadRefund`) |
| Reply inbox | shipped | Unified SMS conversation view across leads, threading by phone number and distinguishing a customer thread from a teammate thread (carried explicitly, not inferred from the name). | `src/app/(app)/reply-inbox/` |
| Contacts list | shipped | Full contact/lead table view (same underlying lead data as pipeline) for browsing/searching outside the kanban board. Server-paged like the dialer and board (DECISIONS #019/#020): the page carries a 60-row window, counted tiles, and a total; search runs server-side over the whole book; the duplicate banner's grouping (`buildDuplicateGroups`, pure and tested) is computed server-side and loaded after first paint; opening a row fetches that contact's card data; select-all-matching is served and capped at 2,000 recipients. | `src/app/(app)/contacts/` |
| Salespeople leaderboard | shipped | Per-rep leaderboard of leads/value with medal icons for the top performers. The tallies are grouped in the database (`rep_lead_stats`, migration 0156 — one row per rep instead of a scan of every lead); until that migration is run the page falls back to the old slim scan, so it keeps working either way. | `src/app/(app)/salespeople/`, `supabase/migrations/0156_rep_lead_stats.sql`, `src/lib/report-leads.ts` |
| Appointment-setter assignments | shipped | Assigns specific leads/contacts to a setter rep for follow-up, independent of the main pipeline owner. | `src/app/(app)/appt-setter-assignments/`, `src/lib/actions/setter-contacts.ts` |
| Appointment reps see the lead | shipped | A sales-scoped rep booked onto a lead's appointment — either chair, `assigned_to` or `second_assigned_to` — holds the lead like the assigned rep, dispatcher and closer do: the contact in their portal, its estimates/contracts with their contents, and (once seated on the contract) their commission line. Closed the same hole 0134 closed for closers: the second chair could see the visit but not the customer it was for. Both SQL visibility rules updated together, pinned by the same test (decision #009, #024). | `supabase/migrations/0152_appointment_reps_see_lead.sql`, `src/lib/data/lead-visibility-rules.test.ts` |
| Lead sources admin | shipped | Company-editable list of lead source values (with merge-duplicate-values tool), used on lead create/edit and reporting. | `src/app/(app)/settings/lead-sources/` |
| Leads webhook (external intake) | shipped | Key-authenticated public endpoint that creates a lead from an external form post (JSON or form-encoded) and fires the new-lead SMS alert. | `src/app/api/leads/webhook/` |
| New-lead SMS alert | shipped | Texts the company's configured alert numbers when a new lead comes in, from whatever channel (webhook, CallRail, inbound email). | `src/lib/notify-new-lead.ts` |
| Contact soft-delete / trash & restore | shipped | Deleting a contact is still a real hard delete with cascades, but everything about to be destroyed is snapshotted as JSON into `lead_trash` first (raw `select("*")`, not the typed `Lead` shape, so untyped columns like the Drive folder link aren't silently dropped on restore), and orphaned-but-not-cascaded rows (events, jobs, texts) are recorded by id so a restore can relink them. | `src/lib/lead-trash.ts`, `src/app/(app)/settings/trash/` |
