| Background polls off the server-action path | shipped | Every recurring poll asks a cheap route handler, never a Server Action: popup alerts (20s, `/api/popup-alerts`), screen-share discovery (20s, `/api/screen-shares`), the device heartbeat (30s, `/api/device-touch`), the notification bell (60s, `/api/notifications`), the lead card's Texts tab (12s while open, `/api/lead-messages`), the presence panel (60s while open, `/api/live-users`) — and the topbar search, which fires on every pause in typing (`/api/search`). Next runs server actions through one queue in the browser, one after another, so a poll on that path put the user's own Save/Send/click behind it — the app-wide "keeps freezing", twice (DECISIONS #029, #062). The rule is enforced by `src/lib/poll-routes.test.ts`, which fails on any `setInterval` in a client component that calls an action. The bell and share polls skip their turn while the tab is hidden and catch up on focus; popup alerts still poll hidden (they own the tab-title count and the ding). Auth unchanged: each route runs the same RLS-scoped action on the caller's cookie session. The popup poll's heaviest read, the incoming-text badge, is reduced in the database by `text_alert_rollup` (migration 0168) — see the Reply inbox row. | `src/app/api/popup-alerts/route.ts`, `src/app/api/notifications/route.ts`, `src/app/api/screen-shares/route.ts`, `src/app/api/device-touch/route.ts`, `src/app/api/lead-messages/route.ts`, `src/app/api/live-users/route.ts`, `src/app/api/search/route.ts`, `src/lib/poll-routes.test.ts`, `popup-alerts.tsx`, `notification-bell.tsx`, `screen-share.tsx`, `activity-tracker.tsx`, `messages-panel.tsx`, `live-users-button.tsx`, `global-search.tsx` |
